# Exact static fragment HMR

Development output can patch a changed static text node or safe static attribute without replacing the component's DOM, effects, handlers, owner or named signal state. Stylesheet-only edits continue to swap their link separately. Production has no fragment metadata or fragment-wrapper import.

The proof has two independent parts. Codegen records byte ranges of its own generated `tpl` HTML literals and masks only those ranges in a copy of the complete generated module. It retains this exact bounded wiring string, not a lossy hash. Runtime requires exact old/new wiring equality and equal browser-parsed template topology, tag/namespace, node count and comment anchors for every template. Source-wide string replacement and approximate DOM morphing never authorize a patch. Source line markers or budget coordinates changing can conservatively invalidate this proof and cause a component remount.

Development template wrappers register pristine node references before dynamic insertions shift child indices. Records belong to the actual reactive owner and disappear on branch/row/instance disposal. Plans validate all affected live targets and their old text/attribute values before writing. Dynamic-owned conflicting content, unsafe attributes, topology/wiring changes and exhausted proof budgets remount a proven owner boundary using named-signal restore behavior. The implementation does not patch newly cloned nodes while old effect closures still point somewhere else.

Allowed static attributes are class, title, alt, placeholder, style, aria attributes and ordinary data attributes. Identity/runtime data markers, event handlers, value/checked/selected/type/name, URLs and other stateful attributes do not qualify. A conflicting current class/style value declines the patch rather than overwriting a dynamic effect's state. Input value, focus and input selection remain untouched during a successful static patch; browser document selection is restored on the same nodes with offsets clamped when text becomes shorter. A changed CSS rule can still intentionally alter layout, visibility or browser focus behavior.

Existing module closures can create an initially inactive branch after a static patch. Its template wrapper reads the live instance's latest template metadata, so that future branch gets the new HTML. Current component implementations are retained in a bounded registry for future mounts through an older imported wrapper; an edit to an unmounted component no longer requires a page reload just to update a future mount.

Bounds are explicit: 64 templates, 64 KiB template text and 64 KiB exact wiring per compiled metadata object; runtime proof visits at most 8192 template nodes with depth 64, and an instance retains at most 8192 pristine node references/2048 fragment records. Exceeding a proof limit declines fragment patching and remounts the component. The current-definition registry has at most 1024 component hashes. Empty live-instance registry sets are removed. Browsers do not expose an API to evict evaluated ESM versions, so the dev client reloads with the explicit `native-module-cache-budget` reason after 256 cache-busting hot imports rather than growing that native module map indefinitely. This is a preventive count budget, not a measured heap-size guarantee.

`brain:hmr` keeps its compatible `kind: 'js'` for JavaScript updates and adds mode, patched/remounted counts and a reason. Modes distinguish static fragment, component remount, mixed update and future-mount-only update. Full reloads are reserved for document/server contracts, module/runtime version incompatibility, failed module import, or the finite native module/definition registry budget; they emit an explicit reason. An arbitrary page reload is not reported as a successful fragment patch.

Node runtime tests verify real node identity, handlers/signals/input state, future branch HTML, owner cleanup, conservative component fallback and absence of a partial text patch before a detected attribute conflict. Codegen tests load emitted modules to compare exact metadata and check zero production metadata overhead. Native browser focus/selection and end-to-end HMR latency remain separate Chrome integration checks; passing the Node DOM shim is not claimed as browser performance evidence.


## Parent-owned row and branch ranges

Before applying any candidate patch, HMR plans all live instances. A list/conditional parent stores its own node range; replacing just a nested child's roots would leave those references stale. An incompatible nested change therefore escalates once to the outermost owned component boundary with a stable mount owner. Multiple changed children under that boundary cause one rebuild. Other candidates covered by that rebuild are not patched first. Keyed moves/removal and conditional toggles then operate on newly captured current ranges; they cannot resurrect the old roots.

The report identifies `ancestor-remount` and `ancestor-remount-for-parent-owned-range`. The ancestor's named state is restored; descendant instances are explicitly recreated rather than mapping ambiguous row states by an unsafe hash/ordinal guess. Safe static fragment updates preserve the existing descendants and their state. If an external/unknown owner range cannot be proven, HMR requests a full reload with `parent-range-owner-unavailable` before changing that range. Empty components retain an invisible anchor so a later first render has a valid insertion point. Normal disposal removes the current HMR roots and deletes empty live-registry entries.

Runtime regressions exercise two changed keyed children covered by one ancestor rebuild, subsequent reorder/removal without stale-root resurrection, current handlers, conditional hide/show after an incompatible update and a null-to-rendered component update. These are functional lifecycle tests, not a measured browser latency result.
