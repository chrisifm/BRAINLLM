# Native backend on the frontend development origin

Set `BRAIN_BACKEND_URL=http://127.0.0.1:8000` in the private resolved development environment to connect an explicitly running native backend. The target accepts only a loopback HTTP origin, without credentials, path, query or fragment. The frontend never invents a database URL, creates a database, migrates schema or launches a backend implicitly. Backend startup/migration and configured allowed frontend origins remain explicit deployment/development steps.

With that configuration, the Rust development server proxies native `/api`, `/_brain` and `/s/` requests through the same origin as the frontend. `/@brain` runtime/HMR/MCP endpoints and source modules remain local. Without configuration the existing frontend behavior is retained. An invalid or unavailable configured backend fails explicitly; it does not quietly answer with fake data or switch native authentication to a legacy signed frontend user.

Only the configured authority receives requests; no user URL, redirect, proxy environment variable or forwarded host selects another destination. The proxy forwards selected application headers, actual Origin, native auth cookies and a new locally generated request ID. It strips client-supplied forwarded identities and unrelated/legacy frontend cookies. The backend still validates authentication, policies and allowed Origin: configure its origin allowlist to the actual frontend origin, including its development port. A port fallback can require updating that explicit allowlist. Production cookies retain Secure/HttpOnly semantics; deployed applications need HTTPS.

Request parsing rejects duplicate headers, ambiguous Content-Length, any request Transfer-Encoding, folded/control headers and unsupported Expect handshakes. Header bytes are capped at 32 KiB, individual lines at 8 KiB. JSON/native requests remain at 64 KiB. Only the exact configured native upload route accepts 5 MiB plus 64 KiB multipart overhead, and oversize requests return 413 before allocating/truncating a body. Retained request-body storage has a global 64 MiB RAII reservation budget.

The native transport has eight in-flight backend operations, a two-second connection deadline, ten-second total backend/response deadline (thirty-five seconds for the native uploads subtree, matching its bounded image/GCS processing window), 20 MiB per response and 64 MiB aggregate buffered response budget. It accepts bounded exact-length and chunked responses, rejects ambiguous framing/unsupported content encodings/trailers, and requests identity encoding. No request is retried behind the caller's back. HEAD keeps the backend's advertised length without buffering a nonexistent body. Native cookie clears and selected response headers are relayed; bodies and credentials are not logged. These are resource-count/byte budgets, not a prediction that unrelated application/browser memory cannot exhaust the machine.

## Native authority in SSR and server functions

The sidecar uses the same exported `nativeAuthBridge` as the production Node runtime. Its fake request/response objects support that bridge's lifecycle without trusting forwarded headers. With native auth configured, a guard-chain request resolves the native `/me` authority once, even when no guard file exists. Its private verified user DTO is passed by the server into the corresponding `load` call, so `load` does not make a second `/me` request. This proof flag is internal sidecar protocol, never a browser parameter, cookie or public manifest.

Independent RPC/form/manual load operations resolve their own authority. Native 401 is anonymous; malformed/unavailable native authority fails rather than trusting a legacy frontend session. `ctx.session.set` remains forbidden for native sessions. Native logout is awaited before returning headers and relays native cookie clears/site-data clearing. Legacy Node session behavior remains available only when native configuration is absent.

The Node runtime's same-origin native proxy provides the analogous production frontend/backend integration; the auth bridge alone is not a public reverse proxy. Neither integration starts a database or grants broad CORS trust. Filesystem/cloud media persistence, provider credentials, HTTPS and real deployment permissions retain their own explicit contracts.

Verification includes a real HTTP authority mock and the actual embedded sidecar runner/exported production bridge: native user overrides a forged frontend role, guard/load uses one `/me`, logout is awaited, native cookie clears are preserved, 401 stays anonymous and unavailable native service returns 503. Rust fixtures additionally cover actual dev routing, private credential selection, strict framing, bounded uploads, chunked/HEAD responses and local runtime route isolation. Source test presence does not assert those Rust fixtures ran; report completed Cargo/browser/database gates separately.


## Rust static production frontend

The existing `Static::load`, `Static::handle` and `serve_static` APIs remain compatible. With `BRAIN_BACKEND_URL` set, the Rust `brain start` static frontend proxies the same native namespaces through its own origin before applying static GET/HEAD restrictions. Its optional `handle_with_backend` entry point accepts an explicit setting for embedding/tests. Target syntax is validated on service startup; nothing creates a database or starts/migrates a backend implicitly.

A base such as `/app` keeps native requests under `/app/api`, `/app/_brain` and `/app/s/`; unprefixed requests do not escape that namespace. Native redirects/cookie clears are relayed, while static assets retain their existing immutable/cache/ETag/Brotli/gzip behavior. Static HEAD uses file metadata without reading the body. Static files stream through a bounded writer instead of allocating an entire asset per connection. The static listener has at most 64 active request threads; request parsing has a total five-second deadline and static response writes a total ten-second deadline. Native operations reuse the fixed-target transport bounds described above. Synchronous filesystem latency itself cannot be guaranteed by a byte/operation budget.

This allows a PM2-managed Rust static frontend and native Rust backend to serve one application origin directly; Nginx remains an optional TLS/edge deployment choice. A Node SSR frontend uses the production runtime's analogous native proxy. Actual deployment, credentials, allowed origins and TLS are explicit configuration, never inferred from generated templates.
