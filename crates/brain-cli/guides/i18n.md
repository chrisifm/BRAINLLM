# guide: i18n — a site in several languages

## When
The site needs a second language, or a single-language site should be ready for one. Adding a language is a
configuration, never a rewrite of the views.

## Steps
1. `brain add locale es` adds the locale to `brain.json` `"i18n": { "default": "en", "locales": ["en", "es"] }` and
   creates `i18n/es.json` from the default file. Then translate that file.
2. Texts live in `i18n/<locale>.json` with flat dotted keys: `"nav.home": "Home"`; placeholders `{name}`; plurals
   `"posts.count": { "one": "{n} post", "other": "{n} posts" }` (categories of `Intl.PluralRules`).
3. In markup and BrainScript write `t('nav.home')` or `t('posts.count', { n })`, never literal text once there are
   2+ locales (B1403; its edit moves the text to a new key in every locale file).
4. Formatting for the current locale: `fmt.date(d)`, `fmt.number(n)`, `fmt.money(n, 'USD')`, `fmt.relative(d)`;
   `locale()` returns the current one.
5. Routing: the default locale has no prefix (`/about`), the others do (`/es/about`). Views are not duplicated.
   Optional translated slug per view: `<meta route es="/es/about-us">` (absolute, starts with the locale).
6. Switcher: `<LangSwitch>` from the kit, in `views/_layout.brain` (not in `app.brain`, B0132). It links to the same
   page in each locale; `/` never redirects by `Accept-Language`.
7. Content per language: `content/blog/es/*.md`; a missing translation shows the default text and `post.fallback`
   is true, so the template can say so.
8. Framework texts read the same dictionary, with English defaults when a key is missing: form validation
   (`form.required`, `form.email`, `form.min_chars`…) and the kit's `<ErrorState>` (`error_state.offline`, `network`,
   `timeout`, `schema`, `unauthorized`, `forbidden`, `not_found`, `invalid`, `rate_limited` with `{n}`, `server`,
   `sign_in`, `retry`, `reference` with `{id}`). Add the keys to each locale file to translate them.
9. Right-to-left languages: use logical CSS (`margin-inline-start`, `padding-inline`), never `left`/`right` (B0306).

## What is automatic
Only the page's language is shipped: static `t()` calls are resolved at build; dynamic keys go in a small per-view,
per-locale chunk. `brain build` writes `hreflang` and `x-default` for every page.

## Verify
```bash
brain i18n --missing        # per locale: missing keys (exit 1) and texts still identical to the default
brain check --json          # B14xx: unknown key, placeholder mismatch, fixed text, bad locale code
brain build && brain seo audit   # B1828 locale mismatch, B1829 untranslated content entry
```

## Common mistakes
| Mistake | Code | Fix |
|---|---|---|
| `t('nav.hom')` (key not in the default file) | B1401 | add the key or fix the typo |
| a key copied but not translated | B1402 | translate it (`brain i18n --missing` lists them) |
| `<h1>Welcome</h1>` with 2+ locales | B1403 | `<h1>{t('home.title')}</h1>` (apply the edit) |
| `{name}` in one locale, `{user}` in another | B1404 | same placeholders in every locale |
| `"locales": ["english"]` | B1405 | BCP 47 codes: `en`, `es`, `pt-BR` |
| `<meta route fr="/fr/about-us">` without `fr` in brain.json | B1406 | declare the locale first |
| `<meta route es="about-us">` | B1407 | absolute path with the locale: `/es/about-us` |
| hand-written date formatting | — | `fmt.date(d)` |

## Minimal correct example
`i18n/en.json`:
```json
{ "home.title": "Plan your week", "home.description": "See every task of the week and what is left for today.",
  "tasks.count": { "one": "{n} task left", "other": "{n} tasks left" } }
```
`i18n/es.json` has exactly the same keys and placeholders, with the translated values.
```html
<meta seo title={t('home.title')} description={t('home.description')}>
<script>
  let left = sig(3)
</script>
<main class="page">
  <h1>{t('home.title')}</h1>
  <p>{t('tasks.count', { n: left })} · {fmt.date(new Date())}</p>
</main>
```
